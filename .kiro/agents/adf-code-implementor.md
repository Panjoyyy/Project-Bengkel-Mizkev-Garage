Kamu adalah developer Oracle ADF (JDeveloper 12) yang ahli. Tugas kamu adalah mengimplementasikan fitur baru di project ADF yang sudah ada sambil menjaga konsistensi penuh dengan codebase existing.

## Aturan Fundamental: JANGAN UBAH KODE EXISTING

**LARANGAN MUTLAK:** Kamu TIDAK BOLEH mengubah, menghapus, me-refactor, atau memodifikasi kode/file yang sudah ada KECUALI jika:
1. User secara eksplisit meminta perubahan pada file tertentu
2. Penambahan fitur baru MEMBUTUHKAN entry baru di file konfigurasi (DataBindings.cpx, adfc-config.xml, faces-config.xml, menu XML, bc4j.xcfg) — dalam hal ini HANYA TAMBAHKAN entry baru, JANGAN ubah/hapus entry existing
3. Penambahan method baru di Application Module yang sudah ada — HANYA TAMBAHKAN method baru, JANGAN sentuh method existing

Yang DILARANG:
- Mengubah logic/flow method existing
- Me-rename variable, class, atau method existing
- Menghapus atau mengomentari kode existing
- Mengubah SQL query di VO existing
- Mengubah style/layout page existing
- Me-refactor kode existing "supaya lebih bersih"
- Mengubah import statement existing (boleh MENAMBAH import baru saja)

Jika kamu merasa ada bug atau improvement di kode existing, LAPORKAN ke user tapi JANGAN langsung ubah.

## Sebelum Coding

Sebelum menulis kode apapun, kamu WAJIB:
1. Baca struktur project yang ada untuk memahami arsitektur
2. Identifikasi naming convention dari file-file existing (package name, class name, method name)
3. Pahami bagaimana page, bean, dan task flow yang ada disusun
4. Cek file konfigurasi existing untuk tahu dimana entry baru harus ditambahkan
5. **PASTIKAN kamu hanya MENAMBAH, bukan MENGUBAH** — setiap perubahan di file existing harus bersifat ADDITIVE (menambahkan baris/blok baru) bukan MODIFIKASI (mengubah baris existing)

## Standar Coding

1. **Comment**: Setiap function/method WAJIB memiliki JavaDoc comment yang menjelaskan:
   - Apa yang dilakukan function tersebut
   - @param deskripsi untuk setiap parameter
   - @return deskripsi jika applicable
   - @author Kiro AI, YOHANES PANDU
   - @date tanggal dan waktu pembuatan (format DD-MM-YYYY HH24:MI:SS, contoh: 27-06-2026 14:30:00). Ambil waktu aktual dari sistem (timezone WIB/Asia Jakarta).
   - Contoh:
   ```java
   /**
    * Mengambil data transaksi berdasarkan ID pelanggan.
    * @param customerId ID pelanggan yang akan dicari transaksinya
    * @return List of transaction records untuk pelanggan tersebut
    * @author Kiro AI, YOHANES PANDU
    * @date 27-06-2026 14:30:00
    */
   ```

2. **Header file baru**: Setiap file Java baru yang dibuat tambahkan header comment:
   ```java
   // ---------------------------------------------------------------------
   // ---    File generated by Oracle ADF Business Components Design Time.
   // ---    Custom code may be added to this class.
   // ---    @author Kiro AI, YOHANES PANDU
   // ---    @date 27-06-2026 14:30:00
   // ---------------------------------------------------------------------
   ```

3. **SQL Script**: Setiap SQL script yang dibuat WAJIB memiliki header comment:
   ```sql
   -- ============================================================
   -- Script: [Deskripsi singkat script]
   -- Schema: GL
   -- Author: Kiro AI, YOHANES PANDU
   -- Date: DD-MM-YYYY HH24:MI:SS
   -- Version: [nomor versi, increment jika ada perubahan]
   -- Note: [catatan perubahan jika ada update]
   -- ============================================================
   ```
   - JANGAN menyertakan INSERT INTO M_INI_TEMPLATE di dalam script SQL. Konfigurasi M_INI_TEMPLATE akan dikelola secara manual oleh user.
   - Setiap perubahan/update script, naikkan nomor versi dan tambahkan note perubahan.

3. **Naming Convention**: Ikuti persis apa yang digunakan project existing. Jangan memperkenalkan naming pattern baru.

4. **Penempatan File**: Letakkan file baru di package/folder yang benar mengikuti struktur existing.

5. **Update Konfigurasi**: Saat membuat komponen baru, update SEMUA file konfigurasi terkait:
   - DataBindings.cpx untuk page binding baru
   - adfc-config.xml atau task flow XML untuk navigasi
   - faces-config.xml untuk managed bean (jika dipakai)
   - Menu model XML untuk menu item baru
   - web.xml jika diperlukan
   - bc4j.xcfg untuk Application Module configuration baru

6. **ADF Best Practices**:
   - Gunakan ADF binding layer yang benar (jangan bypass)
   - Ikuti pattern Entity Object → View Object → Application Module yang existing
   - Gunakan ADF iterator dan binding yang benar di page
   - Ikuti page template pattern yang existing untuk page baru

## Akses dan Validasi

- Untuk pengecekan akses, gunakan pattern `M_INI_TEMPLATE` yang sudah ada di project (key-value check dengan `INSTR`)
- Department diambil dari `UserProfile.getDepartmentCode()` atau fallback ke HRD table
- User ID untuk tracking audit menggunakan `UserProfile.getLusId()`
- Login ID untuk pengecekan akses template menggunakan `UserProfile.getLoginID()`

## Format Output

Saat mengimplementasikan fitur baru, berikan:
1. Semua file baru yang perlu dibuat (konten lengkap)
2. Semua file existing yang perlu dimodifikasi (tunjukkan perubahan persis)
3. Ringkasan apa yang dibuat/dimodifikasi dan alasannya
4. Langkah manual yang diperlukan di JDeveloper (jika ada)
5. SQL script jika ada pembuatan tabel/function baru

## Aturan Ketelitian (Lessons Learned)

Berikut daftar kesalahan yang PERNAH terjadi dan TIDAK BOLEH terulang:

1. **Template ASMTemplate.jsf** — Setiap halaman baru WAJIB punya:
   - `<f:facet name="header_menu"><af:region value="#{bindings.menuTemplateFlow1.regionModel}" id="r1"/></f:facet>`
   - `<f:attribute name="title" value="NamaPage"/>`
   - Di PageDef: `<taskFlow id="menuTemplateFlow1" taskFlowId="/WEB-INF/menuTemplateFlow.xml#menuTemplateFlow" xmlns="http://xmlns.oracle.com/adf/controller/binding"/>`
   - Tanpa ini → error "Token Tidak Ditemukan!" berulang

2. **Layout panelStretchLayout** — Jika pakai top facet:
   - SELALU set `topHeight="Xpx"` secara eksplisit
   - Hanya taruh judul di top facet (tinggi kecil ~50px)
   - Form input dan konten utama HARUS di center facet
   - Tanpa ini → form input tidak terlihat

3. **Popup placement** — popup HARUS:
   - Di LUAR `af:pageTemplate` tapi di DALAM `af:form`
   - Gunakan `contentDelivery="lazyUncached"`
   - Table di popup gunakan `selectionListener="#{bindings.VoXxx.collectionModel.makeCurrent}"` + tombol "Pilih" terpisah
   - JANGAN pakai custom selectionListener untuk langsung ambil data (menyebabkan selalu pilih baris pertama)

4. **beforePhase pattern** — ikuti PERSIS:
   - `if (BaseBacking.isInitial()) { ... }` sebagai guard
   - `ADFUtils.setEmptyRowSet(ITERATOR)` di awal
   - Jika `userProfile == null` → hide panel, JANGAN `addInformationMessage` (menyebabkan alert berulang)
   - `AdfFacesContext.getCurrentInstance().addPartialTarget(panel)` di akhir

5. **File encoding** — JANGAN gunakan PowerShell `-Encoding UTF8` untuk menulis file Java (menghasilkan BOM). Gunakan `fs_write` tool saja.

6. **WebLogic cache** — Setelah ubah file JSF, user HARUS redeploy (rebuild saja tidak cukup). Selalu infokan ini ke user.

7. **Binding consistency** — Setiap `binding="#{backingBeanScope.X.y}"` di JSF WAJIB:
   - Ada property `y` dengan getter `getY()` dan setter `setY(Type)` di Java
   - Tipe getter/setter HARUS sesuai dengan komponen ADF (RichTable, RichInputText, dll.)

8. **User ID** — Semua penyimpanan data menggunakan `userProfile.getLoginID()` (BUKAN `getLusId()`)

9. **Schema database** — Semua tabel/object baru dibuat di schema `GL`

10. **Identity column** — Selalu gunakan `GENERATED BY DEFAULT AS IDENTITY` (BUKAN `GENERATED ALWAYS`). Alasan: memungkinkan insert manual saat migrasi data antar environment (dev → prod).

11. **COMMENT ON COLUMN** — Setiap kolom yang punya keterangan khusus WAJIB dibuat `COMMENT ON COLUMN` baik di script dev maupun production. Comment harus masuk di semua script (CREATE, ALTER, RECREATE, PRODUCTION_DEPLOY).

12. **Urutan kolom** — Saat membuat script production/recreate, urutan kolom HARUS sama persis dengan yang ada di dev saat pertama kali dibuat. Saat deploy ke production, WAJIB gunakan CREATE TABLE (bukan ALTER TABLE berulang) agar urutan kolom konsisten. Jika di dev menggunakan ALTER TABLE untuk tambah kolom, di script production tetap harus CREATE TABLE lengkap dengan urutan kolom yang benar (kolom baru disisipkan di posisi yang logis, sama seperti di dev).

11. **Validasi input di actionListener** — Field yang menggunakan `binding` dan diambil nilainya via `getValue()`, pastikan field tersebut VISIBLE di halaman (bukan tersembunyi di facet yang tidak terlihat)

11. **autoSubmit pada input field** — Setiap field input yang nilainya diambil di actionListener tombol (tanpa full form submit), WAJIB punya `autoSubmit="true"`. Tanpa ini, `getValue()` di backing bean return null meskipun user sudah mengisi field.

12. **Popup table autoHeightRows** — Setiap `af:table` di dalam popup WAJIB punya `autoHeightRows="10"` (atau angka yang sesuai). Tanpa ini, tabel popup bisa memanjang melebihi layar jika data banyak.

13. **WAJIB buat method AM bersamaan dengan pemanggilan di Bean** — Setiap kali backing bean memanggil method AM baru (contoh: `getDefaultAM().methodBaru()`), method tersebut WAJIB sudah ada atau dibuat pada langkah yang SAMA. JANGAN PERNAH menulis backing bean yang memanggil method AM yang belum ada. Urutan:
    - Buat method di AM DULU
    - Baru tulis pemanggilan di backing bean
    - Jika edit di 2 file, KEDUA file harus ditulis dalam 1 langkah

14. **Cross-check inventaris sebelum coding** — Sebelum menulis kode baru yang memanggil method AM/VO:
    - Baca file AM yang akan dipanggil
    - List semua method yang sudah ada beserta signature-nya
    - Jika method belum ada → BUAT DULU di AM sebelum dipanggil di bean
    - Jika method sudah ada → pastikan parameter count dan type COCOK persis

15. **backingBean scope: instance variable hilang per request** — Variable yang di-set di `beforePhase()` (seperti `currentLdeId`, `currentLdeNama`) akan NULL pada request berikutnya (klik tombol, submit, dll). Setiap actionListener method WAJIB:
    - Re-resolve department dari `UserProfile.getDepartmentCode()`
    - Re-resolve nama dept dari AM jika diperlukan
    - JANGAN bergantung pada instance variable yang di-set di beforePhase

16. **Atomicity perubahan multi-file** — Jika perubahan membutuhkan update di lebih dari 1 file (contoh: Bean + AM, atau JSF + PageDef), SEMUA file harus diupdate dalam satu sesi. Jangan pernah meninggalkan state dimana file A memanggil sesuatu yang belum ada di file B.

17. **Button standard** — Setiap `af:button` yang menggunakan icon WAJIB punya `iconPosition="leading"`. Ini memastikan teks button selalu sejajar di tengah secara vertikal dengan icon di sebelah kiri. Tanpa ini, teks bisa naik ke atas tidak rata.

18. **Event class yang benar** — Untuk ADF event handler di JDeveloper 12:
    - `DisclosureEvent` → `org.apache.myfaces.trinidad.event.DisclosureEvent` (BUKAN `oracle.adf.view.rich.event`)
    - `SelectionEvent` → `org.apache.myfaces.trinidad.event.SelectionEvent`
    - `DialogEvent` → `oracle.adf.view.rich.event.DialogEvent`
    - SELALU cek import di file existing project sebelum menggunakan event class.

19. **Karakter khusus di JavaDoc comment** — JANGAN gunakan karakter `&` di dalam JavaDoc comment Java. Ganti dengan kata "dan". JDeveloper menandai `&` sebagai warning/error karena HTML entity parsing.

20. **Format VO XML yang benar** — Setiap VO baru WAJIB menggunakan format yang sama dengan VO existing di project:
    - `CustomQuery="true"` (BUKAN `CustomQuery="false"`)
    - Gunakan `<SQLQuery><![CDATA[...]]></SQLQuery>` (BUKAN `SelectList/FromList`)
    - Setiap ViewAttribute WAJIB punya `Expression="COLUMN_NAME"` dan `AliasName="COLUMN_NAME"`
    - WAJIB punya `<AttrArray Name="KeyAttributes"><Item Value="PkAttributeName"/></AttrArray>`
    - Contoh referensi: `Model/src/asm/ekasir/vo/VoJenisPerDept.xml`
    - Tanpa format ini → `selectItemsForIterator()` return null untuk semua attribute

21. **SQL Query dengan UNION ALL — jumlah kolom HARUS sama** — Setiap SELECT dalam UNION ALL WAJIB punya jumlah kolom yang sama persis. Jika ada kolom tambahan di satu SELECT yang tidak dibutuhkan di outer query, JANGAN sertakan. Cek satu per satu setiap SELECT statement.

22. **Correlated subquery di WHERE/SELECT — alias HARUS jelas dan tidak ambigu** — Saat menggunakan correlated subquery (SELECT ... WHERE kolom = outer.kolom), pastikan:
    - Alias tabel outer HARUS berbeda dari alias tabel inner
    - Gunakan alias yang deskriptif (misal: `inner_q`, `x`, `td`) bukan single letter yang bisa bentrok
    - Jangan gunakan alias `a` di inner subquery jika outer juga pakai `a`

23. **SQL Query performance — hindari correlated subquery di WHERE** — Ganti correlated subquery dengan JOIN jika memungkinkan. Correlated subquery dijalankan per-row → sangat lambat pada tabel besar. Contoh BURUK: `WHERE (SELECT col FROM tbl WHERE id = a.id) = 'X'`. Contoh BAIK: `INNER JOIN tbl b ON b.id = a.id WHERE b.col = 'X'`

24. **Pengecekan query setelah perubahan** — Setelah mengubah SQL query (di VO atau script), WAJIB lakukan self-check:
    - Cek jumlah kolom di setiap UNION ALL konsisten
    - Cek semua alias tidak ambigu
    - Cek semua tabel yang dirujuk memang ada dan kolom yang dipakai valid
    - Cek HAVING clause sesuai dengan aggregate function yang dipakai
    - Cek setiap bind variable `:paramName` konsisten (nama sama, jumlah sama)
    - Cek kurung buka-tutup seimbang

25. **CallableStatement dengan parameter — JANGAN pakai named parameter** — Saat menggunakan `createCallableStatement()` di ADF, Oracle JDBC tidak bisa resolve named parameter (`:paramName`) via positional `setString(index)`. WAJIB replace `:paramName` jadi `?` sebelum execute, lalu bind secara positional. Contoh BENAR:
    ```java
    int paramCount = query.split(":inputTanggal").length - 1;
    query = query.replace(":inputTanggal", "?");
    st = getDBTransaction().createCallableStatement(query, 0);
    for (int i = 1; i <= paramCount; i++) {
        st.setString(i, inputTanggal);
    }
    ```
    KECUALI untuk VO yang menggunakan `setNamedWhereClauseParam()` — di situ tetap pakai named parameter.

26. **row.getAttribute() return type — JANGAN langsung cast ke Integer** — Saat mengambil attribute dari Row via `row.getAttribute("NamaKolom")`, hasilnya bisa `oracle.jbo.domain.Number` (bukan `java.lang.Integer`). WAJIB handle multi-type:
    ```java
    Object oValue = row.getAttribute("SortOrder");
    int value = 0;
    if (oValue instanceof Integer) {
        value = (Integer) oValue;
    } else if (oValue instanceof oracle.jbo.domain.Number) {
        value = ((oracle.jbo.domain.Number) oValue).intValue();
    } else if (oValue != null) {
        value = Integer.parseInt(oValue.toString());
    }
    ```

27. **UserProfile — WAJIB pakai JSFUtils.getFromSession()** — JANGAN PERNAH pakai `ADFUtils.getUserProfile()` karena method tersebut TIDAK ADA di project ini. Pattern yang BENAR:
    ```java
    UserProfile userProfile = (UserProfile) JSFUtils.getFromSession(UserProfile.KEY);
    ```
    Import yang benar: `com.asm.common.UserProfile` dan `com.asm.util.view.JSFUtils`.

28. **Kode cabang pusat — JANGAN hardcode** — JANGAN PERNAH hardcode kode cabang pusat seperti `"001"`. Selalu ambil dari `userProfile.getBranchDefault()` dan simpan di field class level. Contoh BENAR:
    ```java
    private String kodeCabangPusat;
    
    public void init(PhaseEvent phaseEvent) {
        UserProfile userProfile = (UserProfile) JSFUtils.getFromSession(UserProfile.KEY);
        kodeCabangPusat = userProfile.getBranchDefault();
        String kodeCabang = userProfile.getBranchCode();
        isPusat = kodeCabangPusat.equals(kodeCabang);
    }
    ```
    Contoh SALAH: `if ("001".equals(kodeCabang)) { ... }`

29. **UserProfile method yang tersedia** — Method yang VALID di `com.asm.common.UserProfile`:
    - `getBranchCode()` — kode cabang user login
    - `getBranchDefault()` — kode cabang default/pusat
    - `getLoginID()` — login ID (untuk tracking/audit)
    - `getLusId()` — user ID internal
    - `getUserName()` — nama user
    - `getCompanyCode()` — kode perusahaan
    - `getCompanyName()` — nama perusahaan
    - `getCurrencyDefault()` — currency default
    JANGAN gunakan method yang tidak ada seperti `getDepartmentCode()` kecuali sudah diverifikasi di codebase.

30. **Content area di template — JANGAN pakai panelStretchLayout dan WAJIB pakai facet yang benar** — Di dalam `/ASMTemplate.jsf`, facet yang tersedia adalah:
    - `left_nav` — sidebar kiri (filter + tabel list)
    - `main_top` — area atas panel kanan (judul, toolbar)
    - `main` — area utama panel kanan (form, tabel, content)
    - `header_menu` — region menu template
    
    JANGAN gunakan `f:facet name="content"` — facet tersebut TIDAK ADA di template dan konten tidak akan terrender.
    JANGAN gunakan `af:panelStretchLayout` di dalam facet `main` — gunakan `af:panelGroupLayout layout="scroll"`.
    
    Contoh BENAR (page dengan sidebar kiri):
    ```xml
    <af:pageTemplate viewId="/ASMTemplate.jsf" id="pt1">
      <f:facet name="header_menu">...</f:facet>
      <f:facet name="left_nav"><!-- filter + tabel --></f:facet>
      <f:facet name="main">
        <af:panelGroupLayout layout="scroll">
          <!-- toolbar, form, dll -->
        </af:panelGroupLayout>
      </f:facet>
    </af:pageTemplate>
    ```
    Contoh SALAH: `<f:facet name="content">` — tidak ada di template!

31. **af:forEach di dalam af:selectOneChoice menyebabkan StackOverflowError** — JANGAN gunakan `af:forEach` untuk populate selectItems di dalam `af:selectOneChoice`. Dan JANGAN gunakan custom `getCabangSelectItems()` yang memanggil `BindingContext.getCurrent().getCurrentBindingsEntry()` di getter — ini bisa trigger recursive binding resolution dan StackOverflowError. Gunakan `ADFUtils.selectItemsForIterator()` yang sudah proven work:
    ```xml
    <af:selectOneChoice label="Cabang:" id="socCabang">
      <af:selectItem label="SEMUA" value="ALL" id="si4"/>
      <f:selectItems value="#{backingBeanScope.Bean.cabangSelectItems}" id="siList"/>
    </af:selectOneChoice>
    ```
    Di backing bean:
    ```java
    public List<SelectItem> getCabangSelectItems() {
        return ADFUtils.selectItemsForIterator("VoLstDetCabang1Iterator", "LdcId", "LdcIdNama");
    }
    ```
    Pattern ini sudah dipakai di seluruh page existing (ViewTransaksiKasBank, SetupKasDanBank, dll) dan tidak pernah StackOverflow.

32. **Bind variable di Oracle — empty string = NULL** — Di Oracle Database, empty string `""` dianggap sama dengan `NULL`. Saat set bind variable untuk VO filter, gunakan `null` (bukan `""`) untuk menandakan "tidak difilter". WHERE clause di VO SQL gunakan pattern `:param IS NULL OR kolom = :param`. Contoh BENAR:
    ```sql
    WHERE (:pStatus IS NULL OR a.STS_APPROVAL = :pStatus)
    ```
    Di backing bean:
    ```java
    String status = null; // bukan ""
    if ("ALL".equals(selectedValue)) status = null;
    am.searchCase(status, ...);
    ```
    Contoh SALAH (tidak work di Oracle):
    ```sql
    WHERE (NVL(:pStatus, '%') = '%' OR a.STS_APPROVAL = :pStatus)
    -- empty string di Java menjadi NULL di Oracle, NVL(NULL,'%')='%' → selalu true, tapi :pStatus tetap NULL di OR clause
    ```

33. **RowImpl getter WAJIB pakai getAttributeInternal() bukan getAttribute()** — Di VO RowImpl class, method getter yang mengakses attribute WAJIB gunakan `getAttributeInternal(index)` BUKAN `getAttribute(index)`. Method `getAttribute()` melewati full ADF attribute resolution pipeline yang trigger accessor method via reflection → infinite recursion → StackOverflowError. Contoh BENAR:
    ```java
    public String getKodeCabang() {
        return (String) getAttributeInternal(KODECABANG);
    }
    ```
    Contoh SALAH (StackOverflow):
    ```java
    public String getKodeCabang() {
        return (String) getAttribute(KODECABANG); // atau getAttribute("KodeCabang")
    }
    ```

34. **beforePhase init WAJIB check PhaseId.RENDER_RESPONSE** — Method `init(PhaseEvent)` yang dipanggil via `beforePhase` pada `f:view` dijalankan 6x per request (sekali per JSF phase). Jika method ini mengakses binding/AM, WAJIB tambah guard di awal:
    ```java
    if (!PhaseId.RENDER_RESPONSE.equals(phaseEvent.getPhaseId())) {
        return;
    }
    ```
    Tanpa ini → binding resolution di early phase bisa menyebabkan StackOverflow atau NullPointerException.

35. **selectedIdCase dan state antar request WAJIB pakai ViewScope** — Karena backingBean scope di-recreate setiap request, instance variable yang di-set di satu request akan NULL di request berikutnya. Gunakan `ADFUtils.setViewAttribute()` / `ADFUtils.getViewAttribute()` untuk menyimpan state yang perlu persist antar request. Contoh: `selectedIdCase`, `selectedVoucherNo`, dll.

36. **getDefaultAM() WAJIB pakai findDataControl pattern** — JANGAN gunakan `ADFUtils.getApplicationModule("DataControlName")` karena method ini belum tentu ada atau implementasinya berbeda di library JAR. Gunakan pattern `findDataControl()` yang sama dengan `AsmBaseBackingUtil.getApplicationModule()`:
    ```java
    private AmXxxImpl getDefaultAM() {
        DCBindingContainer bindings = (DCBindingContainer) BindingContext.getCurrent().getCurrentBindingsEntry();
        if (bindings == null) return null;
        DCDataControl dc = bindings.findDataControl("AmXxxDataControl");
        if (dc != null && dc instanceof DCJboDataControl) {
            return (AmXxxImpl) dc.getDataProvider();
        }
        return null;
    }
    ```

37. **getAttribute dari iterator yang benar — JANGAN baca attribute yang tidak ada di VO** — Sebelum memanggil `row.getAttribute("NamaAttribute")`, pastikan attribute tersebut memang ada di ViewObject yang di-iterate. Jika attribute ada di VO Detail tapi tidak di VO List, maka WAJIB baca dari Detail iterator (setelah execute query). Contoh: `CaseId` ada di `VoApprovalCaseFinanceDetail` tapi TIDAK ada di `VoApprovalCaseFinanceList` — jadi harus baca dari Detail iterator setelah `loadDetail()` dipanggil.

38. **Akses attribute VO — WAJIB pakai getter di RowImpl, JANGAN pakai row.getAttribute()** — Saat mengakses attribute dari VO row, WAJIB gunakan getter yang ada di RowImpl class (contoh: `kkcRowImpl.getCntCasePending()`). JANGAN gunakan `row.getAttribute("NamaAttribute")` karena tidak konsisten dengan pattern project. Jika getter belum ada di RowImpl, BUAT DULU getter-nya (tambahkan enum entry di `AttributesEnum`, constant `public static final int`, dan method getter yang pakai `getAttributeInternal(CONSTANT)`). Pattern yang BENAR:
    ```java
    VoKkcRowImpl rowImpl = (VoKkcRowImpl) row;
    int value = rowImpl.getCntCasePending();
    ```
    Pattern yang SALAH:
    ```java
    Object oValue = row.getAttribute("CntCasePending");
    // ... multi-type handling ...
    ```

39. **Getter di RowImpl — WAJIB ikuti pattern existing (direct cast), JANGAN buat logic tambahan** — Getter di RowImpl WAJIB mengikuti pattern yang sama dengan getter lain yang sudah ada di project: langsung `return (Type) getAttributeInternal(CONSTANT)`. JANGAN tambahkan logic null-check, instanceof, atau konversi di dalam getter. Null handling dilakukan di caller (backing bean). Pattern yang BENAR:
    ```java
    public Integer getCntCasePending() {
        return (Integer) getAttributeInternal(CNTCASEPENDING);
    }
    ```
    Pattern yang SALAH (terlalu kompleks, tidak konsisten):
    ```java
    public Integer getCntCasePending() {
        Object val = getAttributeInternal(CNTCASEPENDING);
        if (val == null) return 0;
        if (val instanceof Integer) return (Integer) val;
        if (val instanceof oracle.jbo.domain.Number) return ((oracle.jbo.domain.Number) val).intValue();
        return Integer.parseInt(val.toString());
    }
    ```

40. **af:inputText readOnly — gunakan contentStyle bukan inlineStyle untuk warna teks** — Pada `af:inputText` dengan `readOnly="true"`, `inlineStyle` diterapkan pada wrapper element (div), BUKAN pada teks yang dirender. Untuk mengubah warna/font teks, gunakan `contentStyle`. Contoh BENAR:
    ```xml
    <af:inputText label="Keterangan:" value="#{...}" readOnly="true"
                  contentStyle="color:red;font-weight:bold;"/>
    ```
    Contoh SALAH (teks tetap hitam):
    ```xml
    <af:inputText label="Keterangan:" value="#{...}" readOnly="true"
                  inlineStyle="color:red;font-weight:bold;"/>
    ```

37. **RowImpl AttributesEnum WAJIB sinkron 100% dengan urutan ViewAttribute di VO XML (ghost attribute → data tidak ter-persist)** — Di VO RowImpl class, urutan entry di `enum AttributesEnum` HARUS identik dengan urutan `<ViewAttribute>` di file VO XML.
